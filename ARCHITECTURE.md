# Architecture

## The three repositories

| Repo | Runtime | Hosting | Role |
|---|---|---|---|
| `course-web` (this repo) | Next.js | Vercel | Web app, all API routes, all payment/webhook handling, cron jobs |
| `Whatsapp-bot` | Node/Express | Any always-on Node host (currently Render; Railway also works) | WhatsApp Cloud API webhook receiver, lesson delivery, reminders |
| `telegram-bot` | Node/Express | Any always-on Node host (currently Render; Railway also works) | Telegram Bot API webhook receiver, lesson delivery, reminders |

**Both bots require a plan that keeps the process running continuously,
whichever host you use.** They rely on `setInterval`-based reminder
pollers (`pollWorkshopReminders`, `pollLiveClassReminders`,
`sendWorkshopTelegramReminders`) running inside the process at all
times. Free or trial tiers on most platforms — including Render's free
web services, which spin down after 15 minutes with no inbound
request — kill the process during quiet periods, which kills these
timers until something wakes it back up. This isn't a configuration
detail — the reminder feature does not work reliably without an
always-on plan. Check whichever host and tier you deploy to for this
specific behavior before relying on it.

They talk to each other over plain HTTP, authenticated with a single shared
secret (`INTERNAL_BOT_SECRET`) that all three set to the same value:

- `course-web` → bots: when something needs to be pushed to a student right
  now (a workshop confirmation, a payment-confirmed message, a cron-driven
  reminder), `course-web` calls the bot's `/internal/send-*` endpoint with
  `Authorization: Bearer <INTERNAL_BOT_SECRET>`.
- Bots → `course-web`: both bots call back into `course-web`'s API
  (`ACADEMYKIT_URL` — see the naming note below) for things like marking a
  lesson complete, fetching lesson content, or resolving a student's
  enrollment.

All three repos also share direct read/write access to the **same Supabase
Postgres database**, using the service-role key. There is no separate
"bot database" — `course-web`, `Whatsapp-bot`, and `telegram-bot` are three
processes reading and writing the one schema.

### `KURSO_URL` in both bots

Both bot repos read `KURSO_URL`, which must be set to the same value as
`course-web`'s own `NEXT_PUBLIC_SITE_URL`. It's not a separate service —
it's how each bot builds every link it sends a student and how it calls
back into `course-web`'s API (marking a lesson complete, fetching content,
resolving enrollments). Both bots break without it.

## Student identity — two systems, checked independently

A student can be authenticated two completely different ways, and a
meaningful number of protected routes have to check *both*, independently,
because a valid session in one system says nothing about the other:

1. **A bot-issued cookie session** (`kurso_web_session`) — set when a
   student reaches the web app via a signed link generated by one of the
   bots (e.g. tapping "View on web" from a WhatsApp message).
2. **A Supabase Auth Bearer token** — set when a student logs in directly on
   the website (Google login).

A route that only checks one of these will incorrectly deny access to a
legitimately enrolled student who arrived through the other path. When
adding or modifying a protected route, check both paths, and treat them as
**additive**, not alternative-exclusive — having a valid Bearer token should
never invalidate a valid cookie session's access, and vice versa.

## Phone number normalization — the single most fragile piece of this codebase

- **Indian numbers**: stored as a bare 10 digits. No `+91`, no `91` prefix,
  no leading `+`.
- **Every other country**: stored with their full country code digits
  included (e.g. a US number is stored as 11 digits starting with `1`).
- **Meta's webhook** sends phone numbers as `91XXXXXXXXXX` — this prefix
  must be stripped at that specific boundary before the number is used
  anywhere else in the system.
- The canonical normalizers are `src/lib/phone.ts` (course-web) and
  `Whatsapp-bot/phone.js` (kept in sync by hand — there is no shared
  package). **Never write a third phone-normalization implementation.**
  Every place in the code that touches a phone number should call one of
  these two functions, not reimplement the logic.

A known, still-open issue: `EnrollModal.tsx`'s country dropdown lists 14
countries but validates every one of them against a hardcoded 10-digit
length, which is simply wrong for several of those countries (their real
mobile numbers aren't 10 digits). Signup is currently broken for those
countries. This has not been fixed as of this writing.

## Payments — two entirely separate systems that happen to share code

1. **Platform billing** (`KURSO_CASHFREE_*` env vars, `src/lib/kurso-cashfree.ts`,
   `src/lib/kurso-checkout.ts`) — the platform's own Cashfree merchant
   account, used only to collect creator subscription fees and PAYE
   revenue-share invoices. This account belongs to the platform operator,
   not to any creator.
2. **Creator BYOK payments** (`src/lib/gateway-checkout.ts`,
   `src/lib/payment-gateways.ts`) — each creator connects their own
   Cashfree, Razorpay, or Stripe account. Credentials are encrypted at rest
   (`src/lib/creator-secrets.ts`) and never returned to the browser once
   saved. Student payments for courses, ebooks, and workshops flow directly
   into the creator's own account — the platform never holds this money.

Both systems land in the shared webhook handler
(`src/app/api/webhooks/[provider]/route.ts`), which dispatches by
`product_type` (`course`, `ebook`, or `workshop`) to keep the logic for each
product isolated even though they share one entry point.

## Revenue share (PAYE) — how the platform's own commission works

An opt-in alternative to the flat subscription: `src/lib/revenueShare.ts`
computes a commission at the moment of each course or workshop sale, only
for creators with an active row in `revenue_share_agreements`. Everyone
else pays 0% through this mechanism (they're on the flat subscription
instead).

- Base rate applies up to a per-creator paid-customer threshold; a higher
  overflow rate applies beyond it.
- **Course and workshop paid-customer counts are tracked completely
  independently** — crossing the threshold on one does not affect the rate
  applied to the other. Both are measured against the same agreement's
  configured numbers, just counted separately.
- Course and workshop revenue for a given month are combined into **one**
  monthly invoice (`src/app/api/cron/subscription-reminders/route.ts`).
  Unpaid past the grace period pauses new course enrollments *and* new
  workshop registrations for that creator — existing students/registrants
  are never affected.
- Ebook revenue-share is a **separate, unconditional** mechanism — every
  creator selling ebooks owes a flat rate above a small monthly floor,
  regardless of subscription plan, billed as its own separate invoice.
  This is intentionally not the same system as course/workshop PAYE.

## Signed URLs

`src/lib/signer.ts` is the single canonical signed-URL system used
throughout the codebase (lesson video/PDF access, resource links,
bot-generated links). Anything that needs a new kind of signed link should
add a new namespace inside this file rather than building a parallel signing
scheme — collisions between namespaces are a real risk if this rule isn't
followed.

## Database

There are no committed migration files. Every schema change has been a
manually-run SQL statement in the Supabase SQL editor. Before relying on any
assumption about a table's columns, either check a fresh schema export or
search the codebase for every place that table is read/written — the
`database.types.ts` file in this repo is a stub, not accurate generated
types, and should not be trusted.

## Known deferred / incomplete work at the time of this writing

- Per-student burned-in video watermarks and real DRM are deferred — the
  current protection is a signed-URL + overlay-watermark + anti-download
  scheme, not cryptographic DRM.
- Bot delivery of `live_sessions` recordings (distinct from per-lesson live
  recordings) is unbuilt.
- The `EnrollModal.tsx` international phone-length bug described above.
